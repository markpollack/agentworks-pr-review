## Cross-Check: the agent-judge 0.14 release hold — VERIFIED, with two corrections

**Verdict: the dependency claim is TRUE; the migration surface is far smaller than the hold implies; and the
commit attribution in the sibling reports is WRONG.**

### Pinned version
`pom.xml` imports `io.github.markpollack:agentworks-bom:1.15.0`, which pins
**`agent-judge-core` / `-llm` / `-exec` / `-file` at `0.13.0`** (verified in
`~/.m2/repository/io/github/markpollack/agentworks-bom/1.15.0/agentworks-bom-1.15.0.pom` lines 296–315).
`agent-judge-core` is declared without an explicit version, so it inherits 0.13.0. Meanwhile
`~/projects/agent-judge` is at `0.14.0-SNAPSHOT` (HEAD `7bc1298`, 2026-08-12) and **`Verdict.subVerdicts()`
still exists there** — the "no legacy compatibility" ratification is a *decision*, not yet an implemented
removal. Nothing in this repo is broken today.

### `subVerdicts` call-site inventory — 1 file, 2 call sites, 1 method
| Symbol | File | Lines |
|---|---|---|
| `import io.github.markpollack.judge.jury.Verdict` | `src/main/java/io/github/markpollack/prreview/dsl/AssembleReportStep.java` | 22 |
| `verdict.subVerdicts()` (null/empty guard + loop) | same file, `collectJudgments(Object, List<Judgment>)` | 94, 95 |

That is the **entire** `agent-judge` composite surface in this repo. `jury.Verdict` is imported by exactly one
class; no test constructs a `Verdict`; no `Verdict.builder()` / `new Verdict(...)` anywhere in `src/`. Identical
on `origin/v3-serving` @ `b354252`. Everything else from agent-judge is the *leaf* API — `Judgment`,
`JudgmentStatus`, `Check`, `JudgmentContext`, `Judge`, `BooleanScore`/`NumericalScore`, and the
`Jury`/`SimpleJury`/`CascadedJury`/`TierPolicy`/`ConsensusStrategy` construction types — used across ~30 files
and **untouched by a composite-result change**.

### Commit attribution correction
The sibling reports name **`b354252`** as the consuming commit. It is not. `git log -S subVerdicts -- src/`
returns exactly one commit: **`f9696eb` (2026-06-30, "Add modern agent-experiment PR reviewer on the
mapper-enabled JudgeGate")**. `b354252` (2026-08-10) does not touch `AssembleReportStep.java` at all.

### "VerdictRecord migration cost" — a name collision, not an agent-judge cost
`VerdictRecord` in this repo is **`io.github.markpollack.workflow.spec.v3.envelope.VerdictRecord`** — a
**workflow-spec** type (v3 envelope), not an agent-judge type. 3 references: `model/FullReportRequest.java`
(import + record component), `model/EarlyReportRequest.java` (import + record component),
`dsl/AssembleReportStep.java` (javadoc `{@link}` only). Introduced by `ce27d15` (2026-07-28) as part of the v3
DSL authoring, **unrelated to the agent-judge composite surface**. If the hold's cost model attributes
"VerdictRecord migration" to agent-judge, it is counting the wrong dependency.

### The two defects the hold cites — both confirmed against `~/projects/agent-judge`
1. **Composite identity/relation/policy is lost.** `CascadedJury.buildCascadeVerdict` stashes every executed
   tier verdict flat into `subVerdicts` and **discards `stoppedAt` and `tiersExecuted`** (they are parameters
   it never uses). `AssembleReportStep.collectJudgments` then recurses into `subVerdicts` and takes each
   sub-verdict's `individual()` — so the report ends up with a flat `List<Judgment>` in which **which tier
   produced what, which tier stopped the cascade, and each tier's `TierPolicy` are all unrecoverable**.
2. **A throwing tier is silently dropped.** In `CascadedJury.vote`, a non-final tier that throws is logged
   (`"Tier '{}' threw exception, escalating to next tier"`) and `continue`s — `executedTierVerdicts.add(...)`
   is only reached on success. That tier therefore contributes **nothing** to `subVerdicts`, and this repo's
   flattening has no way to notice a tier is missing. The report reads as complete.

### Migration size assessment
**Small — one method, ~10 lines.** A composite-result surface change forces a rewrite of
`collectJudgments` in `AssembleReportStep.java` and nothing else. The realistic cost is not the edit; it is
that `collectJudgments` is the *only* place the tier structure was ever consumed, so whatever replaces
`subVerdicts` must let this repo (a) walk tiers, (b) attribute judgments to a tier, and (c) **observe a tier
that failed to produce a verdict** — the last of which the current API cannot express at all. This repo is
therefore a *cheap* migration but a *load-bearing* design test: it is the only real-world consumer that
flattens a cascade, and it currently produces a silently-lossy report.

**Recommendation to the agent-judge owner**: this repo is not a reason to hold 0.14 on migration cost.
It is a reason to make sure the replacement surface exposes tier identity + policy + a *failed-tier* marker.
